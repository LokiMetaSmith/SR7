# Archived Jules Session Memories

This file is an append-only archive of Jules session memories preserved for ongoing project context and future reference.

## Archival Date: 2026-10-31

* In SRX: eXtream Edition module bridges Shadowrun X (SRX) and Shadowrun 7E. The SRX core engine uses D6 dice pools (5s/6s are hits). 2 dice are always designated as 'Crit Dice' (Double 6s = Critical Hit/+3 hits, Double 1s = Glitch). Damage and Drain are flat values (Magical Drain exactly equals the chosen Force).
* The game rules logic is modularized in `scripts/rules_engine.py` using specific classes like `DiceRules`, `CombatRules`, `MatrixRules`, and `MagicRules`. This replaces the deprecated, monolithic `RulesEngine` class previously located in `scripts/combat_simulator.py`.
* When extracting action logic (like spells, attacks, or matrix actions) from `combat_simulator.py` into rule classes (e.g., `MagicRules`, `CombatRules`, `MatrixRules`), ensure the resolve methods return the expected `(action_text, result_text, edge_spent)` tuple so the main combat loop correctly tracks edge usage and state changes.
* The `GameEnvironment` class parses and stores `layout_ascii` and `legend` from scenario JSON maps to support spatial calculations. During attack resolution in the combat simulator, `CombatRules.calculate_los_cover` uses these properties with a Bresenham-like algorithm to determine dynamic cover bonuses based on Line of Sight.
* When writing deterministic unit tests for combat simulation (e.g., `combat_simulator.py` or `combat_analyzer.py`), invoke the application code directly and use `monkeypatch` to mock `DiceRules.roll_attack_with_edge`, `DiceRules.roll_dice`, `random.randint` (initiative), and `random.random` (action selection) rather than copying application logic into the test body.
* To set up the development environment and run tests, activate the virtual environment, install dependencies (`pip install -r requirements.txt` and `pip install pytest pytest-cov`), set the Python path (`export PYTHONPATH=$(pwd):$(pwd)/scripts:$PYTHONPATH`), and execute `pytest tests` (or `python -m pytest tests/ --cov=scripts --cov=ui` for coverage).
* The project uses GitHub Actions for CI/CD, including a `pytest.yml` workflow (running Python 3.12) that runs the test suite on pushes and PRs to `main`, setting `SDL_VIDEODRIVER=dummy` and `PYTHONPATH` to ensure headless testing of Pygame components.
* When creating execution plans (via `set_plan` or `request_plan_review`), strictly adhere to reviewer rules: 1) Complete all codebase exploration (e.g., `read_file`, `grep`) before generating the plan. 2) Use only granular, actionable tool calls without internal monologue or exploratory steps. 3) Include explicit verification steps (like running test suites or checking file content) immediately after modifying code. 4) Ensure plans are complete with final pre-commit and submit steps.
* The Pygame UI uses a `SoundManager` class in `ui/components.py` to handle background music and sound effects via `pygame.mixer`, utilizing extensive `try/except` blocks (e.g., `if not pygame.mixer.get_init():`) to safely fall back on systems without audio output devices or when sound files are missing.
* The combat simulator (`scripts/combat_simulator.py`) includes a `--trade-simulator` CLI argument to simulate economy haggling. It accepts the format `Combatant_Path:Item_Name:Base_Value:Fixer_Difficulty[:Is_Selling:Condition]` to support both buying and selling with condition markdowns. It uses an opposed Negotiation test to calculate the final price (printed as 'Final Price for [Item]: [Price]'). The Pygame UI integrates this visually via a `TradeScreen` with mode and condition toggles.
* The Pygame UI uses a modular `OverworldMap` component (`ui/components.py`) to render campaign locations. It starts on a 'Campaign Selection' screen rather than booting directly into a map. Upon selection, the map loads a dynamic `nodes` list and a dynamically populated `random_nodes` list (based on a `probability` field) from the chosen `campaign.json` inside its respective `campaigns/<name>/` directory. It triggers an `on_node_click` callback when clicked, passing the entire node dictionary to `load_module` to navigate to the module's path and dynamically handle random encounters based on the `random_encounter` probability parameter defined for each node.
* Shadowrun 7E House Rules for Astral Combat: The simulator tracks plane states using a Plane enum (PHYSICAL, ASTRAL, MATRIX) and an `is_dual_natured` boolean. Astral Initiative rolls REA + INT + 1D6 + MAG. Astral attacks use WIL + Astral Combat versus INT + LOG, and soak with WIL. Base damage is CHA / 2, dealing Stun (S) damage unless the attacker is Dual-Natured or using a Weapon Focus, which deals Physical (P). Astral entities can only target other ASTRAL or DUAL_NATURED entities.
* When writing or expanding narrative files (e.g., novellas in `GM Notes/`), strictly adhere to the 'show, don't tell' principle by incorporating concrete sensory details, observable character actions, and dialogue rather than summarizing internal states.

Similarly, campaign novellas in `GM Notes/` can be exported to PDF using `scripts/generate_novellas_pdf.sh`. * In SRX: eXtream Edition, a 'Unified Possession' rule applies to Riggers jumped into drones, Spirits possessing metahumans, and users overridden by BTL chips. The controller overrides the host's Mental Attributes (WIL, LOG, INT, CHA) but uses the host's Physical Attributes (BOD, AGI, REA). The controller takes half of the host's Physical damage as Stun Biofeedback (resisted with WIL+BOD). If the host is destroyed, the controller is violently ejected (taking 6 unresisted Stun damage and a -2 dice pool penalty for 10 minutes).
* In SRX: eXtream Edition (Digital Essence), Sprites, AIs, and complex Matrix entities possess an Essence of 6 and an Astral Aura (making them vulnerable to Essence Drain; they die/fragment at 0 Essence). Additionally, Magic and Resonance are strictly mutually exclusive for all entities.
* In SRX: eXtream Edition, 'G.O.D. Manifestations' occur if a Hacker rolls a 1 on a Wild Die during an opposed Hacking test. This instantly spawns a physical G.O.D. Antibody (a dual-natured Sprite/Spirit hybrid created by local nanites) directly into physical combat with the Hacker.
* In SRX: eXtream Edition, 'Wild Dice' are rolled alongside the 2 standard SRX Crit Dice. A 6 on a Wild Die explodes into 3 hits, and a 1 on a Wild Die cancels all normal 5s rolled in the current dice pool. 'Unified Saturation' replaces Noise and Background Count with a 'Saturation Level' (1 to 6), forcing characters to replace standard pool dice with Wild Dice equal to this level for Sorcery, Conjuring, Mysticism, Hacking, Software, or Threading tests.
* The Pygame UI (`ui/app.py`, `ui/components.py`, `ui/main.py`) utilizes `pygame.RESIZABLE` and handles input to manage UI components like `PlayerCard`, `GMCard`, `ChatWindow`, `MapGrid`, `OverworldMap`, `TradeScreen`, `SaveLoadScreen`, and `VehicleChaseScreen`. The `App` state is controlled by booleans (`in_campaign_select`, `in_overworld`, `in_trade_screen`, `in_save_load_screen`, and `in_chase_screen`) to transition between campaign selection, overworld navigation, trade markets, state management, tactical combat, and chase minigames. Cards update in place with the game state. It integrates with the combat simulator and feeds user clicks to `app.set_pending_action()` (which handles network multiplayer sync by automatically calling `NetworkManager.send_event` if the user is a client), while free-form chat is handled via `app.pending_chat`.
* In the combat simulator (`scripts/combat_simulator.py`), scenarios can define a `has_stealth_phase: true` flag. During this pre-combat phase, enemies skip turns (patrolling) while players can use 'bypass', 'set trap', or Matrix hacking. In the Pygame UI, `is_stealth_phase_active` is passed down to card components to dynamically render these stealth-specific actions instead of standard combat moves. Stealth is broken seamlessly transitioning to standard combat if a Matrix action critically glitches, or if a loud action (explosive, non-suppressed weapon, or combat spell) is used.
* The `VehicleChaseScreen` Pygame component in `ui/components.py` visually represents relative distance with a dynamic progress bar and interactive `pygame.Rect` bounds for 'Ram' and 'Evade' actions, invoking callbacks that route to `app.pending_action`.
* In `scripts/combat_simulator.py`, the simulation loop waits for UI or networked player input using a non-blocking loop (`while app.pending_action is None: app.tick(); time.sleep(0.01)`) rather than blocking via `input()`. This ensures Pygame and network events are processed continuously.
* The project supports host/client network play. The GM acts as the host, broadcasting the `SimulationState` and `TradeScreen` haggling data, while players connect as clients to view the live game state and submit interactive combat actions back to the GM via `send_event`. CLI scripts (`ui/main.py`, `scripts/combat_simulator.py`, `scripts/run_module.py`) accept `--client` and `--ip <address>` arguments. Network communication is handled by `NetworkManager` in `ui/network.py` using sockets and a custom JSON `NetworkEncoder`.
* Shadowrun 7E House Rules for Metamagic: 'Centering' grants a +1 die bonus to the final dice pool in `roll_dice(pool, wild_dice_count, combatant)`, and 'Shielding' adds its rating (or 1) to the defender's dice pool against spell attacks. The combat simulator's `parse_markdown` extracts metamagics from character stat blocks and appends them to their `special_rules` list.
* Shadowrun 7E House Rules for Technomancers: The 'Gun-Fu (Flow State)' Complex Form allows a character to chain attacks 'John Wick' style; if they reduce an enemy to 0 health, they immediately gain a free attack against another target. In `scripts/combat_simulator.py`, this continuous flow-state combat mechanic is processed by appending the active combatant to a `state.bonus_actions` queue during the combat loop.
* The `scripts/combat_simulator.py` writes checkpoint states to the `campaign_state/` directory as individual JSON files for each combatant (storing fields like `physical_damage`, `stun_damage`, `edge`, `nuyen` types, `faction_standings`, `contacts`, and `weapons`), alongside a `global_campaign_state.json` file for tracking overarching variables like `economy_multiplier`.
